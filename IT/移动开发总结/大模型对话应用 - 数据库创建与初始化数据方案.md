# 大模型对话应用 - 数据库创建与初始化数据分析总结

## 一、现有代码数据库实现概况

### 1.1 实现位置
- 数据库初始化代码位于 EntryAbility.ets 的 onWindowStageCreate() 生命周期方法中

### 1.2 数据库配置
- 数据库名称：ChatRbd.db
- 安全级别：relationalStore.SecurityLevel.S1
- 使用 ArkData 模块的 relationalStore API

### 1.3 当前表结构（CHAT 表）
- ID：INTEGER 类型，主键，自增
- CONTENT：TEXT 类型，非空，存储消息内容
- ISME：BOOLEAN 类型，标识是否为用户发送的消息
- TIME：TEXT 类型，非空，存储时间字符串

### 1.4 初始化数据
- 插入一条默认消息：ID=1, CONTENT="可以开始对话啦", ISME=false, TIME="0:00"

## 二、现有实现流程分析

### 2.1 数据库初始化步骤
1. 定义 StoreConfig 配置对象，指定数据库名和安全级别
2. 定义建表 SQL 语句（CREATE TABLE IF NOT EXISTS）
3. 定义初始化数据 SQL 语句（INSERT INTO）
4. 调用 relationalStore.getRdbStore() 获取数据库实例
5. 判断数据库版本是否为 0（首次创建）
6. 版本为 0 时执行建表、设置版本号为 3、插入初始数据
7. 版本非 0 时跳过初始化

### 2.2 版本管理策略
- 初始版本为 0
- 建表后直接设置版本号为 3
- 通过版本号判断是否需要重新初始化

## 三、现有架构问题分析

### 3.1 数据库与 UI 层未打通
- EntryAbility 中创建了数据库并初始化数据
- Index 页面使用 @State 定义本地状态数组 msgArr
- 页面数据来源于内存初始化，未从数据库读取
- 发送消息后仅更新内存状态，未写入数据库
- 应用重启后历史消息丢失

### 3.2 数据结构不一致
- 数据库表字段：ID, CONTENT, ISME, TIME
- 页面接口定义：id, content, isMe, time
- 字段命名风格不统一（数据库用大写，代码用小驼峰）

### 3.3 数据库初始化位置不当
- 数据库初始化放在 onWindowStageCreate() 中
- 每次窗口创建都会执行 getRdbStore 调用
- 虽然版本判断避免了重复建表，但逻辑应独立封装

### 3.4 缺少数据访问层
- 没有封装 DAO 类进行 CRUD 操作
- 没有 Repository 层统一管理数据源
- SQL 语句硬编码在 Ability 中

### 3.5 数据库版本跳跃
- 版本从 0 直接设置为 3
- 缺少版本 1 和 2 的升级逻辑
- 未来升级路径不明确

## 四、表结构设计分析

### 4.1 当前设计的局限性
- 单表结构，无法支持多会话管理
- 缺少会话概念，所有消息混在同一张表
- 没有消息状态字段（如发送中、发送失败）
- 没有时间戳字段，TIME 使用字符串格式不利于排序

### 4.2 与页面需求的差距
- 页面需要会话列表功能（当前不支持）
- 页面需要历史消息加载功能（当前未实现）
- 页面需要消息持久化（当前未写入）
